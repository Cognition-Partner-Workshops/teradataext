------------------------------------------------------------------------------------------
1. PURPOSE
------------------------------------------------------------------------------------------

teradataext extracts tables from a Teradata Database 16.20 system into pipe-delimited text
files suitable for loading into another database (Amazon Redshift COPY in particular). It:

  * uses FastExport (fexp) for bulk data and BTEQ (bteq) for metadata queries, small
    tables/chunks, LOB tables and as a fallback when FastExport cannot get sessions;
  * splits large tables into chunks and runs several jobs in parallel within a session
    budget;
  * supports incremental (CDC) extraction based on a watermark column;
  * records progress after every chunk so an interrupted or failed run can be resumed;
  * never truncates or silently alters data: a table that cannot be exported losslessly
    is marked failed;
  * writes a metadata file per table, an audit log, archives the output (.tar.gz) and
    prints an executive summary.

It is a lightweight UNIX utility written in bash and POSIX awk: one shell entrypoint
(teradata_extract.sh) and an engine of bash and awk files under lib/. Apart from
Teradata Tools and Utilities it needs only standard UNIX tools (section 2).

------------------------------------------------------------------------------------------
2. PREREQUISITES
------------------------------------------------------------------------------------------

Host
  * Supported systems: Linux, AIX and Solaris, with network access to the Teradata system
    (default port 1025).
  * bash 4.2 or later (bash --version). teradata_extract.sh checks the version at
    startup. AIX and Solaris may ship an older bash or none: install a current bash and
    put it first on PATH, or start the utility as  /path/to/bash teradata_extract.sh .
    On bash 4.2 the scheduler checks for finished jobs every 0.05 s (every 1 s where
    sleep takes whole seconds only), so the next chunk may start up to 1 s later;
    output, state and exit codes are the same.
  * A POSIX awk: gawk, mawk, nawk / onetrue awk (original-awk) or busybox awk. The
    utility runs the command in TDX_AWK, which may include arguments, e.g.
    TDX_AWK="busybox awk". When TDX_AWK is unset the utility uses /usr/xpg4/bin/awk on
    Solaris if it exists (/usr/bin/awk there is the old, non-POSIX awk), otherwise awk
    from PATH. mawk or gawk is recommended for speed (section 13).
  * od, gzip, tar and mkfifo (standard on all supported systems).
  * One SHA-256 tool. The first one found is used, in this order: sha256sum,
    shasum -a 256, openssl dgst -sha256, digest -a sha256 (Solaris).
  * Teradata Tools and Utilities (TTU) 16.20 with FastExport (fexp) and BTEQ (bteq) on
    PATH, or configured with absolute paths in fexp_path / bteq_path.
  * bc (POSIX), only for range chunks on DECIMAL/NUMBER keys with a scale or on integer
    keys longer than 18 digits (section 9). Without bc such a table fails with a clear
    error; other tables are not affected.
  * Disk space in output_dir for the raw export (.raw) of each running job, the .dat
    files and their .tar.gz archive (the .dat files are removed after a successful
    archive check unless keep_raw_after_zip = true).

Startup checks: bash >= 4.2, the awk and od are always checked. gzip, tar, mkfifo, a
SHA-256 tool and fexp/bteq are checked too, except with --status or --help. A missing
item ends the run with exit code 2 before anything is extracted.

Teradata user rights (logon user)
  * SELECT on every source table (or view) to be extracted.
  * SELECT on DBC.ColumnsV, DBC.IndicesV and DBC.StatsV (column, index and statistics
    metadata).
  * CREATE TABLE (and DROP TABLE) rights in logtable_database (or the user's default
    database when logtable_database is empty) for the FastExport restart log tables
    (after a failed FastExport the utility drops its log table with BTEQ, best effort)
    tdx_lt_<hash> (<hash> = the first 12 hex digits of the SHA-256 of the job id; earlier
    versions used SHA-1, so the names differ from theirs).
  * Enough spool space for the largest export query / chunk.
  * The system must allow FastExport (utility) sessions for this user; the number of
    concurrent utility jobs is limited by the system (see section 12).

------------------------------------------------------------------------------------------
3. INSTALLATION
------------------------------------------------------------------------------------------

  1. Copy the utility directory to the host, e.g. /opt/teradataext. The directory that
     contains teradata_extract.sh is the "utility root".
  2. chmod 755 teradata_extract.sh
  3. Check the tools:      bash --version ; fexp -h ; bteq -h
     Choose the awk if the default one is slow or not POSIX (section 2, section 13):
       export TDX_AWK=/usr/bin/mawk
     Optional, no Teradata needed: tests/run_tests.sh --awk "${TDX_AWK:-awk}" runs the
     test suite with fake fexp/bteq tools on this host.
  4. Edit config/main_config.ini (at least [teradata] host) and config/source_tables.ini.
  5. config/process_state.ini.example shows the state format only. The real
     config/process_state.ini is created on the first run; do not copy the example there.
  6. Provide credentials (section 4).
  7. Validate without connecting:   ./teradata_extract.sh --dry-run

The directories data/, metadata/, logs/ and work/ are created as needed.

------------------------------------------------------------------------------------------
4. CREDENTIALS
------------------------------------------------------------------------------------------

Credentials are resolved in this order:

  1. Environment variables TD_USER and TD_PASS, both set: used (PREFERRED).
       export TD_USER=etl_user
       read -s TD_PASS ; export TD_PASS
  2. Otherwise, [teradata] credentials_file, when set. The file must exist, be owned
     by the user running the utility and have no group/other permission bits
     (0600 or 0400).
     Format (see config/credentials.ini.example):
       [credentials]
       user = etl_user
       password = ...
     Keep the file OUTSIDE the utility directory / repository and chmod 600 it.
  3. Otherwise the utility exits with code 2 and a clear message. Setting only one of
     TD_USER / TD_PASS is also an error (exit 2).

The password is never written to disk. Generated fexp/bteq scripts are piped to the tool
on stdin with the real .LOGON line; the copies saved under work/ and every captured tool
output (logs/) have the password replaced by ********.

------------------------------------------------------------------------------------------
5. MAIN CONFIGURATION (config/main_config.ini)
------------------------------------------------------------------------------------------

The file is read by the utility's own INI parser (lib/ini.awk), which accepts a
configparser-compatible subset: key = value, no interpolation. Comments must be on
their own line, starting with # or ;. Inline comments are NOT supported: in
"parallel = 4 ; comment" the value would be "4 ; comment". A different file can be used
with --config PATH.

[teradata]
  host               TDPID (host name or alias) used in .LOGON.
  port               Gateway port (default 1025); used only for the TCP pre-check.
  logmech            Optional logon mechanism (e.g. TD2, LDAP), emitted as .LOGMECH.
  credentials_file   Optional credentials file path (section 4). Empty = env vars only.
  fexp_path          FastExport executable (default fexp). Env TDX_FEXP overrides it.
  bteq_path          BTEQ executable (default bteq). Env TDX_BTEQ overrides it.
  session_charset    ASCII or UTF8. Character columns that are not LATIN (e.g. UNICODE)
                     make the table fail under ASCII; use UTF8 for them. Files are
                     written in the session character set.
  logtable_database  Database for the FastExport .LOGTABLE. Empty = the user's default
                     database. Needs CREATE TABLE rights.
  connect_check      true/false. TCP connect to host:port before starting; failure ends
                     the run with exit 2 before anything is extracted. The message
                     ends with the system's reason in brackets, e.g. "(Connection
                     refused)" or "(Name or service not known)". The check uses bash
                     /dev/tcp; bteq/fexp resolve the host themselves (e.g. COP names)
                     and do not use port, so if bteq logs on but the check fails, set
                     connect_check = false.

[paths]
  base_dir           Base for all relative paths. Empty = parent of the directory holding
                     main_config.ini (the utility root for config/main_config.ini).
  output_dir         .dat and .tar.gz files (default data).
  metadata_dir       .meta.ini files and audit.log (default metadata).
  log_dir            Run log and per-job tool output (default logs).
  work_dir           Generated scripts (password masked), the lock directory
                     .process_state.lock/ and the per-run temporary directory
                     .tdx-run-<pid>/ (default work).
  source_tables_file Table definitions (default config/source_tables.ini).
  process_state_file Machine-managed state (default config/process_state.ini).

[extract]
  file_format             pipe-delimited (the only supported value).
  parallel                Concurrent export jobs (tables or chunks). <= 0 or "auto" means
                          min(number of CPUs, max_sessions). Overridden by --parallel.
  max_sessions            Total Teradata session budget shared by all concurrent jobs.
  min_sessions            Minimum sessions per job; floor for halving on session limits.
  chunk_threshold_rows    Tables estimated above this row count are chunked.
  chunk_rows              Target rows per chunk.
  max_chunks              Maximum chunks per table.
  small_table_rows        Jobs (tables/chunks) estimated below this use BTEQ EXPORT.
  row_estimate            stats = DBC.StatsV statistics, falling back to COUNT(*) when no
                          statistics exist; count = always COUNT(*). Stale statistics only
                          affect chunk planning and tool choice, never the data exported.
  char_trim               CHAR columns only: right (trailing blanks), both, none.
  lob_max_length          Max characters (CLOB/JSON/XML) or bytes (BLOB) per LOB value.
                          A longer value makes the table fail (no truncation).
  max_row_length          Max exported record length in characters; longer = table fails.
                          Capped at 63999 (31999 for tables with UNICODE columns): the
                          record is cast to VARCHAR(limit + 1), and Teradata allows 64000
                          LATIN / 32000 UNICODE characters.
  zip_on_complete         true = archive a table's files as .tar.gz when it is done
                          (section 17; the key name is kept for compatibility).
  keep_raw_after_zip      false = delete the .dat files after the archive passed its
                          integrity check.
  retry_attempts          Session-limit retries per job (section 12).
  retry_delay_seconds     Wait before each session-limit retry.
  session_limit_errors    Comma-separated error codes treated as session-limit failures.
  session_limit_patterns  Comma-separated text patterns (case-insensitive), same purpose.
  bteq_fallback           true = after FastExport session-limit retries are exhausted try
                          the job once with BTEQ EXPORT.
  job_timeout_seconds     Kill a fexp/bteq job running longer than this. 0 = no timeout.
  log_tool_output         masked | errors | none (default masked). What job logs keep of
                          fexp/bteq output. The password is masked in every mode, but masking
                          cannot recognise every transformed echo of it; use errors (only
                          error/failure lines) or none (no tool output; failures report only
                          the Teradata error code) where logs are widely readable.

[format]
  delimiter               Field delimiter (default |).
  null_sentinel           Written for NULL (default \N).
  empty_sentinel          Written for zero-length strings/binaries (default \E).
  escape_char             Escape character (default \).
  big_decimal_quote       Quote around decimals with precision > big_decimal_threshold
                          (default ").
  big_decimal_threshold   Default 18.

  The defaults match docs/DESIGN.md. Changing them changes the file format; loaders must
  be configured to match (see section 20 for the Redshift recommendations).

6. SOURCE TABLE DEFINITIONS (config/source_tables.ini)
------------------------------------------------------------------------------------------

Two kinds of section; section names are free labels.

Table list section (one per database). Only database and table are allowed:

  [sales]
  database = SALES
  table = {REGION, ORDERS, CUSTOMER,
      ORDER_LINES}

  Braces are optional (table = REGION, ORDERS works too). Separate names with commas; a
  long list may continue on indented lines. Listed tables are chunked automatically
  (section 9), have no static filter and are fully extracted every cycle (no CDC), unless
  they also have a one-table section.

One-table section: one table name plus optional settings:

  [orders]
  database = SALES
  table = ORDERS
  cdc_column = UPDATED_TS
  chunk_column = ORDER_ID
  where = ORDER_STATUS <> 'X'
  enabled = true

  database, table   Required. Source database and table/view (table: one name).
  cdc_column        Optional. Enables incremental extraction (section 10).
  chunk_column      Optional. Overrides the automatically chosen chunk column (section 9).
  where             Optional. Static SQL filter ANDed into every export of the table
                    (every chunk). Write it as plain Teradata SQL on one line: a single
                    boolean condition. ';', '--', '/*' and '*/' outside string literals are
                    rejected. The filter runs with the extraction user's rights, so keep
                    source_tables.ini writable only by the operator.
  enabled           Optional, default true. false = the table is ignored.

A table that is in a list section and also has a one-table section: database and table
come from the list (the list always takes priority); cdc_column, chunk_column, where and
enabled come from the one-table section, and a WARNING is logged. enabled = false in the
one-table section therefore switches the listed table off.

Configuration errors (exit code 2): any key other than database/table in a list section,
unbalanced braces or an empty name in a list, a table in two list sections, two one-table
sections for the same table (even if one has enabled = false). Tables are processed in
file order (list members at their list section's position).

The table key used in process_state.ini, in metadata/audit and on the command line is
DATABASE.TABLE upper-cased (SALES.ORDERS); --tables matches it case-insensitively. File
names use <db>_<table> lower-cased with characters outside [A-Za-z0-9_] replaced by _
(sales_orders).

------------------------------------------------------------------------------------------
7. RUNNING THE UTILITY
------------------------------------------------------------------------------------------

  ./teradata_extract.sh [options]

  --config PATH              Main config file (default <root>/config/main_config.ini).
  --tables db.t[,db.t...]    Restrict this run to these tables (case-insensitive).
  --parallel N               Override [extract] parallel for this run.
  --new-cycle                Start a new extraction cycle: every table back to pending,
                             chunk lists cleared, CDC watermarks KEPT.
  --reset-table db.t         Reset one table to pending (chunks cleared, watermark kept).
                             Repeatable.
  --reset-watermark db.t     Additionally clear the table's CDC watermark (its next run is
                             a full extract). Repeatable.
  --dry-run                  Validate config, credentials and tools, print the work queue;
                             does not connect to Teradata.
  --status                   Print the state summary and exit; does not connect.
  -v, --verbose              DEBUG logging on the console.
  -h, --help                 Show the usage and exit.

Environment variables
  TD_USER, TD_PASS   Credentials (section 4).
  TDX_AWK            awk command used by the engine, arguments allowed (e.g.
                     "busybox awk"); default and Solaris rule in section 2. The test
                     suite runs every awk variant through it.
  TDX_FEXP, TDX_BTEQ Override fexp_path / bteq_path (the tests use them for fake tools).

Exit codes
  0    all queued tables done
  1    at least one table failed (others may be done; rerun to resume)
  2    configuration, credential, tool or lock error - nothing extracted
  130  interrupted (Ctrl-C / SIGINT or SIGTERM): the running fexp/bteq jobs are
       stopped, state is saved; resumable

Single-instance lock: only one instance can run against a work directory (and its state
file) at a time. At startup the utility creates the directory work/.process_state.lock/
(mkdir is atomic) and writes its process id to work/.process_state.lock/pid. A second
instance finds the lock held by a running process and ends with exit 2.

If a run was killed without cleaning up (kill -9, host crash), the lock directory stays
behind. The next run sees that the recorded pid is no longer running, removes the stale
lock automatically and continues. To clear a lock by hand, first make sure no instance
is running:

  cat work/.process_state.lock/pid ; ps -p <pid>     (no such process -> stale)
  rm -rf work/.process_state.lock

The pid check only sees processes on the local host: do not share one work_dir between
hosts.

Per-run temporary files (among them the working copy of the state) are kept in
work/.tdx-run-<pid>/ and removed when the run exits.

Examples
  ./teradata_extract.sh --dry-run
  ./teradata_extract.sh
  ./teradata_extract.sh --tables sales.orders,sales.customer --parallel auto
  ./teradata_extract.sh --status
  ./teradata_extract.sh --new-cycle
  ./teradata_extract.sh --reset-table SALES.ORDERS --tables SALES.ORDERS

------------------------------------------------------------------------------------------
8. EXTRACTION STATE, RESUME AND RESTART
------------------------------------------------------------------------------------------

config/process_state.ini is MACHINE-MANAGED. Do not edit it; use the CLI options. It is
rewritten atomically (temporary file in the same directory, then mv, which is an atomic
rename on the same file system) after every chunk and table status change, under the
lock described in section 7, so it is consistent even after a crash or kill.

It holds a [_run] section (cycle_id, last_run_id, last run start/finish), one section per
table (DATABASE.TABLE: status, attempts, method, row estimate, chunk plan, chunks_done,
rows, files, checksum, archive, watermark/pending_watermark, timings, last_error) and one
section per chunk (DATABASE.TABLE/partNNN: status, rows, file, bytes, sha256, method,
sessions, chunk predicate). Status values: pending, in_progress, done, failed.

Resume behaviour (simply rerun the same command):
  * The work queue is the enabled tables (optionally filtered by --tables) whose status is
    not done. Tables already done in the current cycle are skipped.
  * Within a chunked table, chunks already done are skipped; only the remaining chunks
    are exported.
  * Anything found in_progress at startup (the previous run died) is treated as pending
    and redone. Failed tables/chunks are retried on the next run.
  * Exit code 130 (interrupted) and exit code 1 (some table failed) are both resumable.

Restart behaviour:
  * --new-cycle starts a new cycle (new cycle_id, UTC timestamp; suffixed -2, -3, ... if
    that id was already used, so no archive is overwritten): every table back to pending, chunk
    lists cleared. CDC watermarks are kept, so CDC tables export only rows changed since
    the last committed watermark; non-CDC tables are exported in full again.
  * --reset-table DB.T re-extracts one table from scratch in the current cycle (chunks
    cleared, watermark kept).
  * --reset-watermark DB.T also clears the CDC watermark, so the next export of that table
    is a full extract.

------------------------------------------------------------------------------------------
9. CHUNKING
------------------------------------------------------------------------------------------

A table whose estimated row count exceeds chunk_threshold_rows is split into chunks of
about chunk_rows rows: n = max(2, min(max_chunks, ceil(estimated_rows / chunk_rows))).
Range chunking may use fewer chunks when the key range has fewer distinct values than n. Each chunk is an independent job with its own file
<db>_<table>.partNNN.dat (NNN = 1-based chunk number, 3 digits) and its own state.

Chunk column / strategy:
  * chunk_column from source_tables.ini, when set; otherwise
  * a single-column primary key or primary index column of a numeric or DATE type:
    RANGE chunking. MIN/MAX of the column are read and split into contiguous ranges.
    Rows where the column is NULL are included in chunk 1, so no row is lost.
    (chunk_strategy = range)
  * otherwise HASH chunking on the primary index:
      HASHBUCKET(HASHROW(<primary index columns>)) MOD <n> = <chunk - 1>
    (chunk_strategy = hash). Hash chunks are roughly equal when the PI is well
    distributed; a skewed PI gives skewed chunks.
  * unchunked tables have chunk_strategy = none and no .partNNN suffix.

Range boundaries: integer and DATE keys are split with exactly the same formula as in
earlier versions. For DECIMAL/NUMBER keys with a scale, and integer keys longer than 18
digits, the boundaries are computed with bc (section 2; without bc the table fails with a
clear error). Boundaries of keys with a scale are computed with 10 decimal places beyond that scale, so their literals
in the chunk predicates (where in the state file, the work/ scripts) may differ textually
from those of the former engine. Coverage is unchanged: every value, including NULL and
values outside the MIN..MAX read at planning time, still falls into a chunk.

Range chunks on skewed data can be uneven. For tables with a poor PI, set chunk_column to
a well-distributed numeric/date column. The static where filter is ANDed into every chunk.

------------------------------------------------------------------------------------------
10. CDC (INCREMENTAL) EXTRACTION
------------------------------------------------------------------------------------------

For a table with cdc_column:

  1. Before exporting, the upper bound is captured first: MAX(cdc_column) of rows above
     the last committed watermark. It is stored as pending_watermark.
  2. The export selects  cdc_column > watermark  AND  cdc_column <= pending_watermark
     (only the upper bound when there is no watermark yet: first run = full extract,
     including rows whose cdc_column is NULL; if the column has no non-NULL value at all
     the table is extracted in full and no watermark is stored).
     Rows committed in Teradata while the export runs and later than the upper bound are
     picked up by the next cycle, not lost.
  3. The watermark is committed (watermark = pending_watermark) ONLY after the whole table
     (all chunks) completed successfully. A failed or interrupted run keeps the old
     watermark, so the next attempt re-exports the same window.
  4. When there are no new rows, the table completes with 0 rows and the watermark is
     unchanged.

Watermark text format: integers plain, DATE YYYY-MM-DD, TIMESTAMP
YYYY-MM-DD HH:MI:SS.ffffff. The audit log records watermark=<from>-><to>.

Notes:
  * Each cycle produces files with only the changed rows; the target load must merge
    (upsert) them. Deletes in the source are not captured.
  * Rows with a NULL cdc_column are taken only by the initial extract; incremental cycles
    cannot see them. Use a NOT NULL cdc_column, or --reset-watermark for a full reload.
  * The cdc_column must be maintained on insert and update. Rows updated with a value at
    or below the watermark (e.g. back-dated timestamps) are missed.
  * Use --new-cycle for each new incremental cycle; --reset-watermark for a full reload.

------------------------------------------------------------------------------------------
11. FASTEXPORT VS BTEQ SELECTION
------------------------------------------------------------------------------------------

  * BTEQ is always used for metadata queries (columns, indexes, statistics, counts,
    min/max, LOB and row-length checks, CDC upper bound).
  * Data exports use FastExport (multi-session) except:
      - jobs (whole tables or chunks) estimated below small_table_rows: BTEQ EXPORT
        (FastExport start-up overhead and utility slots are not worth it);
      - tables with LOB columns (CLOB, BLOB, JSON, XML): always BTEQ EXPORT;
      - FastExport jobs that still hit a session limit after all retries, when
        bteq_fallback = true: one final attempt with BTEQ EXPORT.
  * method in the state file records fexp, bteq, or mixed (chunks used different tools).

------------------------------------------------------------------------------------------
12. SESSION-LIMIT RETRY
------------------------------------------------------------------------------------------

Teradata limits concurrent utility (FastExport/load) jobs and sessions. A job failure is a
session-limit failure when the tool output contains "Failure <code>" or "Error <code>"
with a code in session_limit_errors (default 2633, 3130), or any of
session_limit_patterns (case-insensitive).

  * A session-limit failure is retried after retry_delay_seconds with
    sessions = max(min_sessions, sessions // 2), up to retry_attempts times.
  * Then, for FastExport jobs with bteq_fallback = true, once via BTEQ EXPORT.
  * Any other failure is not retried within the run: the chunk/table is marked failed
    and is retried on the next run.

[VALIDATE] The codes and message texts vary with the database release and the site's
workload management (TASM/TDWM) rules. Check session_limit_errors and
session_limit_patterns against your system's message catalog and real fexp/bteq output.

------------------------------------------------------------------------------------------
13. OUTPUT DATA FILE FORMAT, ESCAPING AND RAW DECODING
------------------------------------------------------------------------------------------

  * File: data/<db>_<table>[.partNNN].dat; no header line.
  * Encoding: ASCII (session_charset = ASCII) or UTF-8 (UTF8).
  * One record per row, fields separated by |, records terminated by LF.
  * NULL is written as \N. A zero-length string or binary value is written as \E.
  * Inside text values, \ | CR and LF are escaped with a preceding \ :
       a\b -> a\\b      a|b -> a\|b      line break -> \ followed by the LF
    (Redshift COPY ... ESCAPE compatible). A raw LF preceded by an odd number of \ is
    data, not the end of a record.
  * Decimals with precision above big_decimal_threshold (18) are quoted: "12345...67.89".
  * Binary values are hexadecimal text.

Example (ORDER_ID INTEGER | NAME VARCHAR | NOTE VARCHAR | AMOUNT DECIMAL(20,2)):
  1001|ACME Corp|Rush \| fragile|"123456789012345678.25"
  1002|\N|\E|"15.00"
  1003|Smith \\ Sons|\N|\N
Row 1002: NAME is NULL and NOTE is an empty string. Row 1001: NOTE is "Rush | fragile".

During export the tool writes <final>.raw (binary record layout); it is converted to the
.dat file and removed. Row counts are taken from the raw file and must match the counts
reported by fexp/bteq, otherwise the job fails.

Raw decoding
  The raw file is read with od (od -An -v -tu1, run with LC_ALL=C) and decoded by
  lib/rawdecode.awk, run with the awk selected by TDX_AWK (section 2). The layout (with or
  without the record-length prefix and end-of-record byte) is auto-detected; the job
  fails when no layout fits the whole file. Every byte passes through unchanged, except
  that a NUL (0x00) byte inside a record fails the job: portable awks cannot write NUL
  bytes, and the utility never drops or alters data silently (section 19).

  Decoding runs after the export of each job (table or chunk) has finished, as part of
  that job, so it adds to the job's elapsed time. Jobs running in parallel decode
  independently, each with its own od | awk pipeline.

Decoder performance
  Measured decoder throughput for a 48 MB raw file with 200,000 records:

    mawk                                            ~4 MB/s
    gawk                                            ~3.3 MB/s
    onetrue awk (typical AIX/Solaris nawk-class)    ~1.2 MB/s
    busybox awk                                     ~0.6 MB/s
    (former engine, for comparison                  ~230 MB/s)

  For example, 1 GB of raw export takes about 4 minutes to decode with mawk and about
  14 minutes with a nawk-class awk. Recommendations:
    * Install mawk or gawk where available and select it, e.g.
        export TDX_AWK=/usr/bin/mawk
    * For big tables, run more jobs in parallel: raise parallel (and max_sessions, if
      the Teradata system allows it) and lower chunk_rows so that the table is split
      into more chunks; each job decodes its own chunk, using about one CPU.
    * [VALIDATE] Throughput depends on the CPU and the data; measure on your host.

------------------------------------------------------------------------------------------
14. TYPE MAPPING
------------------------------------------------------------------------------------------

Teradata type (DBC code)       Encoding          Output rule             Redshift type
------------------------------ ----------------- ----------------------- -----------------

                                                 after length check

  BLOB (BO)                                      BLOB: length check
anything else (UDT, ARRAY..)   unsupported       table fails             -

Never lossy - the table fails (status failed, last_error set) instead of truncating when:
a LOB value exceeds lob_max_length, a record exceeds max_row_length, a column type is
unsupported, or a non-LATIN character column is exported with session_charset = ASCII.

Numbers are always written without digit grouping (1025, not 1,025), whatever FORMAT the
source column has. An unbounded NUMBER column is the exception: it is written as Teradata
converts it, so check its formatting on the source (the meta file notes this).

Teradata limits on the generated SQL:
  * Text values are escaped with OREPLACE, which returns at most 8000 characters. A text
    value (CHAR, VARCHAR, CLOB, JSON, XML) longer than 8000 characters after escaping
    fails the table with Teradata error 9134.
  * Each column is cast to its longest possible output (text: twice its length, at most
    8000) and the columns are joined into one record. If these widths add up to more than
    64000 characters (32000 for tables with UNICODE, JSON or XML columns), the table fails
    before any export with "table too wide to export".

Time zones: TIME/TIMESTAMP WITH TIME ZONE values are converted to UTC and written with a
trailing Z; the metadata records source_timezone = per-value offset, converted to UTC.
TIME and TIMESTAMP without time zone are written as stored (no conversion).

------------------------------------------------------------------------------------------
15. METADATA FILE (metadata/<db>_<table>.meta.ini)
------------------------------------------------------------------------------------------

Written for every extracted table. [table] section: database, table, extracted_at,
column_count, row_estimate, row_estimate_source, primary_index, chunk_strategy,
chunk_column, chunk_count, cdc_column, session_charset, file_format, delimiter,
null_sentinel, empty_sentinel, escape_char, record_terminator, timezone_policy = UTC.

One [column.NNN] section per column in ordinal order: name, position, source_type
(e.g. DECIMAL(38,2)), td_type_code, nullable, char_set, output_encoding, redshift_type,
null_sentinel (\N), empty_sentinel (\E or n/a), empty_string_possible (yes/no),
source_timezone (time zone types only), notes.

Use redshift_type to generate target DDL, and output_encoding / empty_string_possible to
decide how each column must be loaded (section 20).

------------------------------------------------------------------------------------------
16. AUDIT LOG (metadata/audit.log)
------------------------------------------------------------------------------------------

Append-only; one line per table per run:

  <utc iso ts> | <run_id> | <DB.TABLE> | <done|failed|skipped> | rows=<n> | files=<n> |
  chunks=<done>/<total> | method=<m> | elapsed=<s>s | watermark=<from>-><to> | <message>

(one physical line; wrapped here). skipped = already done in the current cycle.

------------------------------------------------------------------------------------------
17. ARCHIVE (.TAR.GZ), INTEGRITY TEST AND RAW FILE DELETION
------------------------------------------------------------------------------------------

With zip_on_complete = true, when all chunks of a table are done its .dat files are
archived into data/<db>_<table>_<cycle_id>.tar.gz (earlier versions wrote a .zip). The
config keys zip_on_complete and keep_raw_after_zip and the state keys zip_file and
zip_sha256 keep their names for compatibility; they refer to the .tar.gz archive.

The archive is built and checked with standard tools only (no GNU tar -z):

  1. tar cf - <the table's .dat files> | gzip -c > <name>.tar.gz.tmp
  2. gzip -t <name>.tar.gz.tmp                 the compressed stream is intact
  3. gzip -dc <name>.tar.gz.tmp | tar tf -     the member list must equal the
                                               table's .dat file names
  4. the file is renamed to <name>.tar.gz and its SHA-256 is recorded as zip_sha256
     (SHA-256 tool: section 2).

Only after these checks, and only when keep_raw_after_zip = false, are the raw .dat
files deleted. checksum_sha256 in the state file is the SHA-256 over the per-chunk
SHA-256 hex strings joined by LF, in chunk order; each chunk's sha256 is in its
[DB.TABLE/partNNN] section.

Verify an archive by hand:

  gzip -t data/sales_orders_<cycle_id>.tar.gz
  gzip -dc data/sales_orders_<cycle_id>.tar.gz | tar tf -
  sha256sum data/sales_orders_<cycle_id>.tar.gz     (compare with zip_sha256; or
                                                     shasum -a 256, openssl dgst -sha256,
                                                     digest -a sha256)

Unpack portably (works with the tar of Linux, AIX and Solaris):

  mkdir -p /stage/sales_orders && cd /stage/sales_orders
  gzip -dc /opt/teradataext/data/sales_orders_<cycle_id>.tar.gz | tar xf -

19. TROUBLESHOOTING
------------------------------------------------------------------------------------------

First look at last_error (--status), the run log and the per-job tool log in logs/.
Message texts below are typical; [VALIDATE] against your release's message catalog.

Exit code 2 (nothing extracted)
  * "credentials" - set both TD_USER and TD_PASS, or fix credentials_file
    (exists, owned by you, chmod 600).
  * "tool not found" - fexp/bteq not on PATH; set fexp_path/bteq_path or fix PATH.
  * bash older than 4.2, or awk, od, gzip, tar, mkfifo or a SHA-256 tool missing -
    install it or fix PATH; select the awk with TDX_AWK (section 2).
  * connect check failed - host/port wrong, DNS, firewall; test: nc -vz <host> 1025.
  * lock - another instance is running (its pid is in work/.process_state.lock/pid).
    A stale lock left by a killed run is removed automatically; see section 7 to clear
    one by hand.
  * configuration error - message names the file/section/key; remember: no inline
    comments.

Teradata errors
  2633  Too many load/unload tasks running now. System utility-job limit reached
        (session-limit failure: retried with fewer sessions, then BTEQ fallback). Lower
        parallel/max_sessions or run outside busy load windows.
  3130  Response limit exceeded (too many open responses/requests for the user). Treated
        as a session-limit failure by default. Lower parallel.
  8017  The UserId, Password or Account is invalid. Bad logon: check TD_USER/TD_PASS or
        the credentials file, logmech (e.g. LDAP), and whether the user is locked.
  3523, 3524
        Access-rights errors: the user (or, for a view, the view's owning database)
        lacks a right on an object or database. Grant SELECT on the source table/view
        (with GRANT OPTION to the view owner where views are used), SELECT on
        DBC.ColumnsV/IndicesV/StatsV, and CREATE TABLE on logtable_database. The
        message names the missing right and object.
  3807  Object '<name>' does not exist. Wrong database/table in source_tables.ini,
        missing access to the object, or logtable_database does not exist.
  2646  No more spool space. Chunk the table more (lower chunk_rows) or ask for spool.
  3706  Syntax error. The generated SQL was rejected: report it with the work/ script,
        the tool log and the Teradata release.
  3798  A column or character expression is larger than the max size. The generated SQL
        is wider than Teradata allows: report it as for 3706.
  9134  Result exceeded maximum length (OREPLACE): a text value is longer than 8000
        characters after escaping (section 14). Export the table through a view that
        shortens or splits the column.
  The run summary and audit log show the first numbered "*** Failure NNNN" (or
  "*** Error NNNN") line from the tool output, not BTEQ notices such as
  "*** Error messages now directed to STDOUT.".

Table marked failed (exit 1)
  * "LOB value length ... exceeds lob_max_length" - raise lob_max_length (mind
    max_row_length and the target's 65535 VARCHAR limit) or exclude the table.
  * "record length ... exceeds max_row_length" - raise max_row_length if the tools and
    target allow it.
  * "unsupported type" - UDT/ARRAY/etc.: export through a view that casts the column.
  * "table too wide to export" - the column widths add up to more than one Teradata
    VARCHAR (section 14). Export the table in two views with fewer columns each, or
    through a view that casts wide text columns shorter.
  * "bc is required for range chunks on this key" - install bc (section 2), or set
    chunk_column to an integer or DATE column.
  * non-LATIN column with ASCII - set session_charset = UTF8.
  * row count mismatch / raw layout not recognised - check the tool log; report it with
    the work/ script and tool versions.
  * NUL byte in a record - a value contains a 0x00 byte, which cannot be written by a
    portable awk (section 13). Export the table through a view that removes or replaces
    the byte in the affected column, or converts the column to hex [VALIDATE].
  Fix the cause and rerun: done chunks are skipped.

Slow jobs
  * A long gap between the end of fexp/bteq (tool log) and the chunk being marked done
    is raw decoding. Use mawk or gawk (TDX_AWK) and more, smaller chunks (section 13).

20. LOADING INTO AMAZON REDSHIFT
------------------------------------------------------------------------------------------

[VALIDATE] Everything in this section must be validated on the target cluster with real
extracted samples (including NULLs, empty strings, embedded |, \ and line breaks, big
decimals, time zone and binary columns) before production loads.

Create target tables from the redshift_type values in the .meta.ini files. Upload the
.dat files (unpacked from the .tar.gz, section 17) to S3, then load with COPY:

  COPY sales.orders
  FROM 's3://my-bucket/extract/sales_orders.part'
  IAM_ROLE 'arn:aws:iam::123456789012:role/MyRedshiftRole'
  DELIMITER '|' ESCAPE NULL AS '\\N'
  DATEFORMAT 'YYYY-MM-DD' TIMEFORMAT 'auto'
  ENCODING UTF8;

  (ENCODING UTF8 also reads ASCII files.) In Redshift string literals a backslash is
  doubled, so '\\N' denotes the two characters \N.

ESCAPE makes COPY turn \| into |, \\ into \ and \<LF> into a line break, which is exactly
how the utility escapes text. Two default settings are NOT compatible with ESCAPE:

  * Empty strings: with ESCAPE, the sentinel \E is read as an escaped E and loads as the
    letter "E" - indistinguishable from a real value "E".
  * Big decimals: values with precision > 18 are written as "123.45" (quoted). Without the
    CSV option the quotes are data, so loading them into DECIMAL columns fails.

Option A (recommended) - direct load. Extract with these [format] settings:

  empty_sentinel =
  big_decimal_quote =

An empty string is then an empty field (Redshift loads an empty field into CHAR/VARCHAR
as an empty string unless EMPTYASNULL/BLANKSASNULL are used; do not use them) and NULL
remains \N. Big decimals are plain numbers and load into DECIMAL(p,s) directly. Use the
COPY above unchanged. Values longer than the target column, and DECIMAL values with
precision > 38 (mapped to VARCHAR), need attention in the DDL.

Option B - keep the default format and load into a VARCHAR staging table, then decode.
Do NOT load with ESCAPE and then try to repair: e.g. CASE WHEN col = 'E' THEN '' ... is
WRONG, because after ESCAPE a real "E" and an empty string look the same.

Correct staging approach: load WITHOUT ESCAPE into a staging table whose columns are all
VARCHAR(65535), so every field arrives exactly as written in the file, then decode:

  CREATE TABLE stage.orders (order_id VARCHAR(65535), name VARCHAR(65535),
                             note VARCHAR(65535), amount VARCHAR(65535));

  COPY stage.orders
  FROM 's3://my-bucket/extract/sales_orders.part'
  IAM_ROLE 'arn:aws:iam::123456789012:role/MyRedshiftRole'
  DELIMITER '|' NULL AS '\\N' ENCODING UTF8;

  INSERT INTO sales.orders (order_id, name, note, amount)
  SELECT CAST(order_id AS INTEGER),
         CASE WHEN name = '\\E' THEN '' ELSE REPLACE(name, '\\\\', '\\') END,
         CASE WHEN note = '\\E' THEN '' ELSE REPLACE(note, '\\\\', '\\') END,
         CAST(TRIM(BOTH '"' FROM amount) AS DECIMAL(20,2))
  FROM stage.orders;

  (In the SQL literals '\\E' is the two characters \E, '\\\\' is \\ and '\\' is \.)

LIMITATION of option B: without ESCAPE, COPY does not understand \| or an escaped line
break, so a text value containing |, CR or LF splits the record and the load fails or is
misaligned. Option B is therefore only valid for tables whose text values contain no |,
CR or LF; otherwise use option A. Check the data (e.g. grep -c '\\|' on the .dat file is a
quick hint) before choosing B. Hex columns (binary) are loaded to VARCHAR in staging and
converted to VARBYTE as appropriate (e.g. FROM_HEX) [VALIDATE].

Further target notes [VALIDATE]:
  * TIMESTAMP values use a 'T' separator (YYYY-MM-DDTHH:MI:SS.f); TIMEFORMAT 'auto'
    is expected to accept it.
  * TIMESTAMPTZ/TIMETZ values are UTC with a trailing Z.
  * FLOAT values use 17 significant digits and E+nnn exponents (FLOAT8).
  * Binary columns are hexadecimal text for VARBYTE columns.
  * Columns with empty_string_possible = no in the metadata never contain \E.
  * For CDC cycles, COPY into a staging table and MERGE into the target.
  * After loading, compare row counts with rows/rows_exported in the state file and the
    audit log.
